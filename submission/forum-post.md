### 一、自我介绍

我是一名计算机专业的学生，本次**单人参赛**。

> 【以下两段是作品动机的表述，请本人按真实经历确认或改写后再发布。】

学生阶段写一个页面，"做完了"的判断标准通常只有三条：能显示、能点击、和设计稿对得上。
至于这个页面**别人**用起来怎么样——尤其是看不清屏幕的人、不用鼠标的人——
普通开发流程里没有任何一个环节会提醒我们：控制台干干净净，页面渲染正常，测试全绿，障碍对写代码的人是不可见的。

无障碍规范（WCAG）的条文是公开的：`contrast ratio ≥ 4.5:1`、`提供可访问名称`、`焦点可见`。
但对学生开发者来说，这些句子容易停在"知道对"这一层——`SC 1.4.3` 那段文字背得下来，
写代码时依然会顺手挑一个好看的浅灰；自动化审计工具能给分数和一堆报错，照着改完还是不理解**为什么**这是障碍。

这个项目想解决的就是这一段：**能不能做一个让学生开发者"亲手撞上一次"的工具。**
不是再多一份规范清单，而是把缺陷做成可以真的打开、真的走一遍键盘、真的改一笔的网页，
改完当场看到差别，然后还能把这段代码带走用在自己的项目里。

AccessLab 无障碍实验室就是从这个念头做出来的，全程用 Qoder 开发、用 Qoder Sites 部署。

### 二、你的作品是什么

**一句话：AccessLab 是一个给学生开发者用的网页无障碍动手实验室——在真实的网页组件上发现障碍、动手修好、当场看到差别、把代码带走。**

谁在什么场景下用它：

| 谁 | 什么场景 |
| --- | --- |
| 学生前端开发者 / 前端初学者 | 学完 HTML/CSS 会写页面，但不知道怎么判断"这个页面别人能不能用" |
| 课程 / 社团组织者 | 需要一个能直接发给同学、点开就能动手做的练习页面 |
| 校园产品维护者 | 想知道自己那套配色的正文和按钮，是不是根本看不清 |

它由三个实验和一个报告组成：

**1. 色彩对比度实验**
默认给你一对特别常见的颜色：正文灰 `#777777` 压在白底 `#FFFFFF` 上。看起来挺正常，
实测对比度 **4.48:1，未达 WCAG 2.2 普通文本 AA 的 4.5:1**。差 0.02。
点「生成修复建议」，算法向黑或向白二分逼近、取改动最小的达标色，给出 `#767676` → **4.54:1 达到 AA**。
应用到预览、撤销回原状、复制可粘贴的 CSS，三步都能真实回退。
所有数值都由页面里的 WCAG 2.2 相对亮度算法实时计算，**不是写死的结论**。

**2. 表单标签实验**
一个"学生信息登记"示例表单。姓名上面那行字**故意**只用一个 `<span>`：
你在屏幕上看得见"姓名"，但它和输入框之间没有任何关联，读屏软件念到那个输入框时可能只说"编辑框"。
点「重新检测」，结论是从浏览器**真实 DOM** 里读出来的，而且明确区分两件常被混淆的事——
「缺少关联的可见标签」和「完全没有可访问名称」不是一回事（placeholder 能给到名称，但不算正确关联的可见标签）。
点「修复标签关联」，DOM 真的变成 `<label for="student-name">`：`input.labels` 从 `0` 变成 `1`、
点那行字能聚焦到输入框、复检问题数归 0，而你输进去的内容一个字都没丢。
修复前后的 HTML 并排对比、真正改动的那几行高亮、可以复制，展示的 `id` / `for` 就是页面此刻在用的值。

**3. 键盘焦点实验**
这一页请你把鼠标放到一边。三个按钮都能用 Tab 走到，但缺陷态的 `:focus-visible` 写了 `outline: none`——
**焦点确实在这儿，可你在屏幕上看它在哪儿都行，就是看不出它在哪儿。**
按 Tab 依次走过去，试着说出自己选中了哪个按钮，大多数时候说不出来。
点「修复焦点指示」，同一批按钮、同一套行为，只把焦点规则换成 `outline: 3px solid #4338ca; outline-offset: 3px`。
再按一遍 Tab：这次看得见。页面会分别记录修复前后的键盘到达次数，走完五步人工验证后你自己点「我已完成观察」。
这个缺陷样式**只作用在实验区那几个按钮上**，站点自己的导航和按钮焦点始终是可见的——
把整站的焦点样式关掉来制造教学效果，本身就是造障碍。

**4. 统一成果报告**
三个实验跑完，`#/report` 把这次会话的成果汇总起来，四项计数是**分开**的：
已记录 / 已实际执行修复 / 已进行修复后复核（含人工键盘体验）/ 仍需人工验证。
其中"人工验证"又拆成三组，互不冒充：**仍等你本人完成的观察**、**你已确认完成的观察**、
**建议你另外用真实辅助技术去验的项**——点了"我已完成观察"只会让键盘实验那一条进第二组，
绝不会因此把"NVDA 实测通过"写进报告。
报告可以复制或下载成 Markdown，内容和页面上展示的**逐字同源**，全程在浏览器本地完成、不上传任何数据。

**整个产品的主张就是这条动线：体验问题 → 动手修复 → 重新验证 → 带走代码。**

它不是一个静态科普页，也不是一个把规范条文换个排版的博客。每一处检测都是真的在跑，每一处修复都是真的在改 DOM 或样式。

### 三、为什么做

**问题的来源很朴素：学生开发者手上没有"发现自己造了障碍"的手段。**

判断一个页面"做完了"的标准，通常是：能显示、能点击、和设计稿对得上。
这套标准隐含了一个很强的假设——**看这个页面的人，视力正常、并且用鼠标**。
一旦来人不符合这个假设，页面就安静地把他挡在外面了，而且**开发者不会收到任何报错**：
控制台干干净净，页面渲染正常，测试全绿。障碍对写代码的人是不可见的，对使用者才是真实的。

> 【下面三段是从缺陷本身推出的后果，不是用户访谈或真实用户测试的结论。本项目没有做过任何用户调研，也不引用调研数字。】

低视力用户面对浅灰正文，问题不是"有点费眼"，而是**这段字读不下来**；
键盘使用者面对 `outline: none`，问题不是"少了个框"，而是**不知道刚才那一下按到了哪个按钮，
只能一直按 Tab 直到浏览器换页，或者干脆放弃**；
读屏用户面对没有关联的标签，问题不是"少了行说明"，而是**焦点落进输入框也不知道它要填什么**。

**为什么现有学习方式不够用。** 学生能接触到的路径大致三类：读 WCAG 条文、看科普文章、跑自动化审计工具。
读条文的问题是不落地的抽象——规范写的是判定条件，不是"我这一行代码会怎么伤人"；
科普文章读完留下印象，但轮到自己挑颜色时不会触发；
审计工具给一个分数和一堆报错，改完之后仍然不理解**为什么**这是障碍，
而且它离学生的真实开发场景太远：不会为了改一个颜色去装一整套审计流水线。

**AccessLab 的做法是把抽象规范换成一次亲手上手。**
不告诉你"浅灰不行"，把浅灰放在你眼前，你自己调、自己看数值、自己算出那个只多 0.06 的达标色，
然后你就再也忘不掉 4.5:1 是什么意思了。键盘那一页也不替你看，直接说：请把鼠标放到一边。

**技术向善在这件事上具体是什么。** 无障碍的一个残酷现实是：它的成本极低、收益极不对称。
把 `#777777` 改成 `#767676` 是一个字符，把 `<span>` 换成 `<label for>` 是加两个属性，
删掉一条 `outline: none` 是删一行 CSS。**加起来不到十分钟。**
而对另一些人来说，这十分钟决定了这个页面他能不能用。
所以我认为这件事的杠杆点不在"多做几个审计工具"，而在**让更多人第一次动手的时候就顺手做对**。

还有一层是这个项目做到后面越来越清楚的：**做无障碍的产品，自己必须先是无障碍的。**
AccessLab 在真实浏览器的键盘事件下可以只用键盘走通、有跳到主内容的 skip link、有语义化 landmark、
标题层级不跳级、站点自身的焦点环始终可见、在 `prefers-reduced-motion: reduce` 下不播动效、状态不只靠颜色区分。
这些是"自动化浏览器测试 + DOM / 可访问性树核对"层面的结论——
**系统级减弱动效开关下的实际观感、真机读屏下的播报，仍属未验证项**（见第五部分第 9 节）。
它们不是给评委看的装饰，是它作为教学工具的可信度本身。

**一点明确的自我限制。** 我没有做过用户访谈，也没有真实用户测试数据，本帖不引用任何调研数字。
我也没有条件用真机读屏软件跑一遍——所以产品不会声称"NVDA / VoiceOver 实测通过"。
AccessLab 只对它内置的示例做教学性检测与修复，**不提供整站 WCAG 合规认证**。
报告页上逐字写着：「本报告仅针对 AccessLab 内置示例，不是网站 WCAG 合规认证。」
一个教人别夸大结论的产品，自己最不能先夸大结论。

### 五、用 Qoder 做出来的过程

2026 年 11 月 16–19 日，四个自然日、8 个开发阶段，单人、全程 Qoder。
我按"哪些事我交给它、哪些事必须我自己定"来说，因为这大概是最有价值的部分。

#### 1）需求拆解与验收口径：我来定，Qoder 来落实

这个项目最怕的不是做不出来，是**做出来一个骗人的东西**——
把写死的数字当成检测结果、把"改了提示文字"说成"真的修好了"、把没测过的说成测过。
所以我在 `PRD.md` 里给每个模块都写死了"不得越界声明"，例如：
色彩实验只判定普通文本 AA 一条，结论不得外推为整页合规；报告不得出现总分、百分比、"整体合规"字样。
Qoder 把这些约束逐条变成代码里的行为和**可执行的断言**，而不是文档里的一句话。

#### 2）真实检测逻辑：Qoder 写实现 + 单元测试，我核标准

- **对比度算法**：Qoder 用 WCAG 2.2 相对亮度公式实现 `contrast.ts`，配单元测试。
  过程中它主动指出了 sRGB 线性化阈值的历史差异（WCAG 2.0/2.1 正文写 `0.03928`，现行定义 `0.04045`），
  并说明这个差异不落在任何 8 位整数通道上、对所有可选颜色结果完全相同——我核对规范原文后采纳现行值。
- **修复建议**：`colorRepair.ts` 向黑 / 白二分逼近、取 RGB 改动最小者，并用同一份算法复核达标；
  **绝不写死建议色**。`#777777 → #767676 / 4.48:1 → 4.54:1` 就是它算出来的。
- **表单检测**：`formLabelAudit.ts` 只读浏览器真实 DOM，因此"修复"之后复检的结论会真的变化。
  我特意要求把「缺少关联的可见标签」和「完全没有可访问名称」分成两条显示，
  并且让电子邮箱在同一份报告里显示为通过——用来证明检测器不是一律报红。

#### 3）键盘交互：Qoder 实现，真实浏览器取证

这一天我给自己定了条规矩：**不许拿 jsdom 的结果冒充键盘体验。**
Qoder 用真实浏览器（headless Edge 157 / Chrome 158）+ CDP 的**键盘事件**（`Input.dispatchKeyEvent`）走完整条 Tab 序列，
每一站同时读 `getComputedStyle` 的实际 `outline` 值和 `:focus-visible` 是否匹配。
缺陷态示例按钮实测 `outline: none 3px`、修复后 `solid 3px`；站点外壳的 skip link / logo / 五条导航都是 `solid 3px offset 2px`。

> **这一节能证明什么、不能证明什么**：它证明的是**真实浏览器在收到 Tab 键事件后的焦点变化、键盘顺序与计算样式**，
> 是真实内核的渲染与焦点行为，不是 jsdom 的模拟；
> 它**不能**证明真人手按实体键盘的观感，也**不能**证明读屏软件会怎么播报——那两项仍在未验证清单上。

#### 4）Bug 发现与迭代修复：这一轮最有价值的三个

- **非法输入下的状态一致性（Day 2）**：输入 `#12zz` 时，页面仍在显示上一次的达标建议——等于拿一个过期结论骗人。
  我先让 Qoder 补一条**会失败的测试**把它钉住，再做最小修复：非法值一出现，旧建议与旧快照立即失效、修复区暂停、
  生成按钮消失；改回合法值后**不自动复活**，必须重新生成。
- **CSS 打进产物的文字泄漏（Day 2）**：构建产物里出现了只存在于文档里的句子。查出来是文案进了 CSS 层。修完复建、比对哈希。
- **操作后焦点退回 `<body>`（Day 7，真实键盘测试才抓得到）**：三个实验页里五个主操作
  （生成建议 / 应用修复 / 撤销 / 修复标签关联 / 修复焦点指示）会用结果块**顶掉原按钮**；
  按钮一消失，浏览器就把焦点丢回 `<body>`——**键盘用户既看不见焦点落在哪，也读不到刚才那次操作的结论。**
  这个缺陷自动化断言里完全看不出来（功能都对、数值都对），是在真实浏览器里逐站发送 Tab 键事件、逐站读 `activeElement` 才暴露出来的。
  修法：结果块加 `tabindex="-1"` 并主动 `focus()`，把焦点交给新出现的那一块；
  同时守住三条边界——结果块**不进入 Tab 顺序**、**不新增播报区**、位置仍在原操作区内。
  改完实测：五个动作的焦点分别落在「建议 · 尚未应用」/「修复已应用」/「已撤销本次修复…」/「标签关联已修复…」/「已应用焦点修复」，
  下一次 Tab 落在同区下一个可用控件。

#### 6）我自己的判断，AI 不会替我做

有几处是我不同意或压住 Qoder 的：

- 报告页的"人工验证"原来只有一栏。我觉得这不够诚实：用户点了"我已完成观察"，
  系统就把该项算作已完成，同时又把 NVDA / VoiceOver 那种根本没做过的验证混在同一句提示里。
  我要求拆成三组、且**每组的"（N 项）"必须等于它真正列出的条目数，页面 / Markdown / 测试共用同一份数组**，
  数字不许手抄。
- 顶部导航在宽屏下实测 36px。Qoder 起初写成"未达 WCAG 要求"。我核了规范：
  WCAG 2.2 **SC 2.5.8** 的最低值是 24×24 CSS px，**SC 2.5.5** 的 44px 是 AAA 档建议。
  44px 是我们的自设设计目标，可以照它改，但**不能声称小于 44px 违反 WCAG**。
  改是改了（全断点统一 44px，20 组实测通过），但措辞按规范口径修正。
- 色彩页「生成修复建议」这一步不写入任何播报区。加一个 `aria-live` 很容易，但它会和既有读数区双播报。
  我选择先补焦点交接（用户能自己读到结果块），把"要不要加播报"留到真机读屏结果出来再定，
  并在文档里明说这条**未被读屏证明**。
- 台账**不做持久化**。刷新就回到 `0 / 3` 看着像缺陷，但它换来一个干净承诺：不存任何东西、不上传任何东西。
  我没有为了"体验更顺"引入 `sessionStorage`，只把空状态改成了"先去哪个实验"的引导。
